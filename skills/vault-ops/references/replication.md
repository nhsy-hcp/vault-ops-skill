# Replication: DR and performance secondaries

Read this when the cluster replicates (`health.replication` shows a DR or performance mode other than `disabled`), when the user names a DR or performance (PR) secondary, or when findings include VT-HLTH-002 or VT-REPL-*.

## Running against replicated clusters

- For a DR pair, run `health` against both nodes (set `VAULT_ADDR` to each node in turn) and `audit`/`inventory`/`usage`/`entities` against the primary only: a DR secondary rejects authenticated reads by design.
- A performance (PR) secondary accepts authenticated reads, so every subcommand works there. Tokens are per cluster (they don't replicate): the user needs a token minted on that secondary (the `vault-ops-readonly` policy itself replicates from the primary). Run `health` against the primary and each secondary; paths filters and the lag/heartbeat view are only on the primary.

## Reading replication data in `health.json`

- `health.replication.{dr,performance}.mode/state`, plus `secondaries[].connection_status` on a primary and `primaries[]` / `connection_state` on a secondary.
- Replication blocks also carry `corrupted_merkle_tree`, `last_wal` (primary) / `last_remote_wal` (secondary), `known_secondaries` (primary), and per peer `last_heartbeat`, `clock_skew_ms` and `replication_primary_canary_age_ms` (how old the newest replicated write is on that peer); addresses and cluster IDs are never collected. On a performance primary, `health.replication.performance.paths_filters[]` (`secondary_id`, `mode` allow/deny, `paths`, `dynamic_filtered_mounts` count) lists what doesn't replicate to each secondary; `null` means unreadable (see coverage). `health.performance_secondary: true` means the node is a performance secondary: all data was read normally (it serves authenticated reads, unlike a DR secondary, so an audit there is valid; say so when asked), but its inventory differs from the primary's by design (local mounts are that cluster's own; filtered namespaces/mounts are absent), and client counts and tokens are its own. VT-REPL-* findings cover lag, secondaries with no heartbeat since the primary started (VT-REPL-002: never connected, or down since a primary restart; VT-HLTH-002 still reports them as disconnected, so never suggest revoking on that alone; VT-HLTH-002 names its peers in `evidence.disconnected_peers`, so say explicitly which peer it is about and that the other, connected peers are not affected by it), clock skew, a corrupted merkle tree and paths filters; replication fixes are read-only investigation, and never suggest `promote`/`demote`/`failover` or any other replication write. `health.dr_secondary: true` means only unauthenticated status was readable (license, lease, raft, audit device, snapshot and metrics data are `null` by design, not missing permissions).
