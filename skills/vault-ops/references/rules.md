# Rule catalogue and remediation

Each rule ID is permanent. Remediation is **drafted for a human to run** — never execute it. Replace `<ns>`, `<path>`, `<name>` from the finding's `namespace` and `object`. For a child namespace, prefix commands with `VAULT_NAMESPACE=<ns>` (or `-namespace=<ns>`).

| rule_id | Sev | What it means | Draft remediation | Watch out for |
| --- | --- | --- | --- | --- |
| VT-MOUNT-001 | medium | Mount runs a plugin marked `deprecated` / `pending-removal` / `removed` (`evidence.deprecation_status`). | Plan migration to the replacement engine; enable it alongside, migrate clients, then `vault secrets disable <path>` / `vault auth disable <path>` in a change window. | `removed` plugins stop working on upgrade — check before any Vault upgrade. |
| VT-AUTH-001 | low | Auth mount is listed in the UI login page for unauthenticated callers. | `vault auth tune -listing-visibility=hidden <path>` | Harmless for public login methods (e.g. OIDC) that users must see; confirm intent before changing. |
| VT-MOUNT-002 | low | Mount `max_lease_ttl` exceeds the cluster ceiling (`evidence.baseline_source`: `cluster` or `fallback` 768h). | `vault secrets tune -max-lease-ttl=<baseline> <path>` (auth: `vault auth tune -max-lease-ttl=<baseline> <path>`) | Existing leases keep their TTL; lowering it affects new leases/renewals only. If `baseline_source=fallback`, the token could not read `sys/config/state/sanitized` — say so. |
| VT-MOUNT-003 | info | Mount is `local`: not replicated to performance secondaries / DR. | Usually intentional (per-cluster data). If not, data must be recreated on a replicated mount — `local` cannot be changed after enable. | Only meaningful when replication is in use (see health). |
| VT-MOUNT-004 | low | Mount explicitly sets `default_lease_ttl` above 768h (`evidence.default_lease_ttl_seconds`, `evidence.threshold_seconds`). Mounts that inherit the cluster default are not flagged. | `vault secrets tune -default-lease-ttl=<value> <path>` (auth: `vault auth tune -default-lease-ttl=<value> <path>`) | Existing leases keep their TTL; only new leases/renewals change. Usually fires with VT-MOUNT-002 (a default above 768h needs a raised max); fix both in one change. Clients can still ask for a TTL up to the max. |
| VT-MOUNT-005 | info | More than 20 non-built-in mounts of one type in a namespace (`evidence.mounts_by_type`). One finding per namespace and mount kind (auth/secrets). | No catalogue command: consolidate into fewer mounts with per-path ACL policies (for KV, one mount with a path per app). Moving data means re-writing secrets into the new mount; the operator should plan it per engine. | Some sprawl is deliberate (per-team PKI, per-tenant transit keys). Large mount tables slow namespace operations and replication. |
| VT-MOUNT-006 | info | KV mount is version 1 (`options.version` missing or `1`): no versioning, soft delete or check-and-set. | `vault kv enable-versioning -namespace=<ns> <path>` | The mount is unavailable while it upgrades, and v2 API paths gain `data/` and `metadata/`: update ACL policies and any client that calls the API directly first. Cannot be reverted. |
| VT-NS-001 | info | Namespace has only the token auth backend. | If users/apps should log in here, enable an auth method (`vault auth enable -namespace=<ns> oidc`); otherwise accept — child namespaces often rely on parent auth + entity groups. | Normal for admin-boundary namespaces (e.g. tenant roots). |
| VT-NS-002 | info | Leaf namespace with only built-in engines and no children — appears unused. | Confirm with the owner; if unused, `vault namespace delete -namespace=<parent> <name>` in a change window. | Deletion is irreversible and removes everything inside; never suggest without owner confirmation. |
| VT-SNT-001 | low | Sentinel policy is `advisory`: logs, never blocks. | `vault write sys/policies/<egp\|rgp>/<name> enforcement_level=soft-mandatory policy=@<file> [paths=...]` after testing. | Raising enforcement can block traffic; test in a lower environment first. |
| VT-SNT-002 | info | Sentinel policy is `soft-mandatory`: a sudo token can override. | Consider `hard-mandatory` if overrides are not part of the operating model. | Same blocking risk as above. |
| VT-SNT-003 | info | EGP path is `*` — applies to every request in the namespace. | Narrow `paths` to the endpoints the policy governs. | A hard-mandatory wildcard EGP that can evaluate false locks out everyone, including admins. |
| VT-SNT-004 | low | Sentinel policy body always evaluates true (`main = rule { true }`). | Replace with a real rule or delete the policy (`vault delete sys/policies/<kind>/<name>`). | It looks like a control in policy lists but enforces nothing. |
| VT-LIC-001 | medium | License expires within 90 days (`evidence.days_remaining`). | Obtain a renewed license, update it on every node (`license_path` / `VAULT_LICENSE_PATH` / `VAULT_LICENSE`), then run `vault license reload` (or restart). | After expiry there is a grace period before termination; check `termination_time` in health output. |
| VT-HLTH-001 | medium | Node sealed, or HA enabled with no active leader. | Sealed: unseal per runbook (auto-unseal: check KMS reachability). No leader: check raft peers `vault operator raft list-peers` and logs. | Run checks against each node; one sealed standby may be fine behind a load balancer. |
| VT-HLTH-002 | medium | DR/performance replication enabled but its state is not healthy (`evidence.state`), or a peer is not `connected` (`evidence.disconnected_peers`). | `vault read sys/replication/<dr\|performance>/status` on both clusters; check the peer is up and unsealed, the cluster port (8201) path between them, and WAL gaps (`last_remote_wal` vs primary `last_wal`). | Read-only investigation only; never suggest `demote`/`promote`/`failover` without an incident runbook. A secondary that is restarting shows as disconnected briefly. |
| VT-LEASE-001 | low | Cluster `default_lease_ttl` is above 768h (`evidence.default_lease_ttl_seconds`): every mount that inherits it issues leases this long. | No catalogue command: lower `default_lease_ttl` in the server configuration on every node, then reload or restart. The operator should confirm the exact steps in the Vault configuration docs. | Not reported for a DR secondary or when `sys/config/state/sanitized` is unreadable. An unset default (Vault's built-in 768h) does not fire. Existing leases keep their TTL. |
| VT-HLTH-003 | info | Vault version older than the supported window (`evidence.min_supported`). | Plan an upgrade path following HashiCorp's upgrade guides (step through required intermediate versions). | `min_supported` is a constant in the script — may be stale. |
| VT-HLTH-004 | medium | Raft autopilot reports the cluster unhealthy, or a server unhealthy (`evidence.unhealthy_servers`, `evidence.failure_tolerance`). | `vault operator raft list-peers` and `vault operator raft autopilot state`; check the unhealthy node is up and unsealed, its `last_contact` and trailing logs against `last_contact_threshold` / `max_trailing_logs`, and the cluster port (8201) path to the leader. | Read-only investigation only; never suggest `remove-peer` without an incident runbook. A node that just joined or restarted is unhealthy until `server_stabilization_time` passes. |
| VT-HLTH-005 | low | The queried node reports irrevocable leases (`evidence.irrevocable_leases`): Vault tried to revoke them and gave up, so the credentials may still be valid at the backend (database, cloud, PKI). | Read-only investigation: `vault read sys/leases/count type=irrevocable` and `vault read sys/leases` (lists irrevocable leases with their error), then fix the backend cause (connection, deleted role, permissions). Once the credentials are cleaned up at the backend, an operator can drop the leases with `vault lease revoke -force -prefix <prefix>`. | `-force` removes leases from Vault **without** revoking anything at the backend: only after manual cleanup, per runbook. From `health.metrics` (`sys/metrics`): the lease gauges exist on the active node only, so a standby is not judged. |
| VT-HLTH-006 | medium | The queried node reports more outstanding leases than the review threshold (`evidence.leases`, `evidence.threshold`, 100,000). Large lease counts slow unseal, leader election and lease expiration. | Find where they come from: `vault read sys/leases/count type=all include_child_namespaces=true` and `vault list sys/leases/lookup/<prefix>`. Then shorten TTLs on the busiest mounts (see VT-MOUNT-004), move high-volume short-lived clients to batch tokens, and cap growth with a lease count quota (`vault write sys/quotas/lease-count/<name> path=<mount> max_leases=<n>`, Enterprise). | The threshold is a heuristic; large clusters run more. Judged from the active node only. Revoking leases in bulk can overload backends: never suggest it as the fix. |
| VT-AUD-001 | medium | No audit device is enabled (`sys/audit` readable and empty). | No catalogue command: enable at least one audit device (file, syslog or socket) with the operator's log pipeline. The operator should confirm the device options in the Vault audit device docs. | Not judged when `health.audit_devices` is `null` (DR secondary, or the token lacks `read`+`sudo` on `sys/audit`; check coverage). Enable a second device at the same time (see VT-AUD-002). |
| VT-AUD-002 | low | Exactly one audit device is enabled (`evidence.device_path`, `evidence.device_type`). If Vault cannot write to it (disk full, socket down), Vault refuses every request. | No catalogue command: add a second device of a different type or target, so one failing sink doesn't block requests. | Vault only blocks when **every** enabled device fails. Two devices on the same disk share the same failure. |
| VT-AUD-003 | medium | Audit device writes sensitive values in clear (`evidence.log_raw: true`) or token accessors unhashed (`evidence.hmac_accessor: false`). | Options can't be changed in place: enable a replacement device with safe options first, then `vault audit disable <path>`. | Disable the old device only after the new one is writing, or the cluster can briefly lose its only device (VT-AUD-001/002). Existing log files still hold the clear values; treat them as sensitive and rotate per policy. |
| VT-SNAP-001 | medium | Enterprise cluster on integrated storage has no automated snapshot config. | No catalogue command: create an automated snapshot config (`sys/storage/raft/snapshot-auto/config/<name>`) writing to storage off the cluster nodes (object storage). The operator should confirm the storage options in the Vault docs. | Judged only on Enterprise with raft readable; CE and other storage backends are skipped. Manual or externally scheduled `vault operator raft snapshot save` jobs aren't visible to this check, so ask before assuming there are no backups. |
| VT-SNAP-002 | medium | Automated snapshot is failing (`evidence.consecutive_errors` > 0) or overdue: no run for more than max(interval, 25h) past `evidence.next_snapshot_start` (`evidence.overdue_seconds`). | Read-only investigation: `vault read sys/storage/raft/snapshot-auto/status/<name>` (the error text is deliberately not in the findings), then check storage target reachability, credentials and free space. | The status's `next_snapshot_start` stays stale after a config change until the next run, so an interval changed to longer than a day can fire falsely until then. A config that has never run isn't judged. |
| VT-SNAP-003 | info | Automated snapshots are written to the node's local disk (`file` URL scheme). | No catalogue command: move the config to object storage, or confirm the local path is copied off the node. | A lost or rebuilt node takes its local snapshots with it. Fine for dev and test clusters. Judged from the last run's URL, so a config that has never run isn't judged. |
| VT-ID-001 | low | Identity entity has no aliases: no login maps to it (orphaned, or created by hand and never linked). | Confirm with the owner. If unused: `vault delete -namespace=<ns> identity/entity/id/<entity_id>`. If it should be used, link a login: `vault write -namespace=<ns> identity/entity-alias name=<login> canonical_id=<entity_id> mount_accessor=<accessor>`. | Groups or policies on an orphan grant nothing until an alias exists. Check `group_count` before deleting. |
| VT-ID-002 | info | Policies attached directly to an entity (`evidence.policies`). | Move the policies to an identity group and add the entity as a member, then `vault write -namespace=<ns> identity/entity/id/<entity_id> policies=""`. | Removing direct policies before the group grant exists cuts access; do it in that order. |
| VT-ID-003 | info | Entity is disabled: tokens tied to it are refused. | If the identity is gone for good, delete the entity; if temporary, record why and when it should be re-enabled. | Disabling is a common offboarding step. It isn't a problem by itself, only stale. |

### Client and identity anti-patterns

These come from `usage` (VT-CLI-*) and `entities` (VT-ID-004/005). They point to how workloads authenticate, not to a single setting, so most remediation is an investigation. The skill cannot read auth role configuration: the operator confirms the cause.

| rule_id | Sev | What it means | Draft remediation | Watch out for |
| --- | --- | --- | --- | --- |
| VT-ID-004 | low | A namespace has at least 100 entities and more than 3× its active entity clients (`evidence.entities`, `evidence.active_entity_clients`). Active = the higher of the billing period and the current month. | Run `entities --namespace <ns> --list` to see which alias mounts the entities come from. Check those auth roles for a per-run identity (a JWT/OIDC `user_claim` that changes per job, one AppRole per instance) and fix it at the source. Then remove stale entities after owner review: `vault delete -namespace=<ns> identity/entity/id/<entity_id>`. | Not judged when no activity is recorded (activity log disabled or new cluster). A recently created namespace or a long billing period can skew the ratio. |
| VT-ID-005 | low | The same alias name is on several entities in one namespace through different auth mounts (`evidence.shared_alias_names`, `evidence.entities_affected`). Each entity is a separate billable client. | Merge the duplicates into one entity: `vault write -namespace=<ns> identity/entity/merge from_entity_ids=<id> to_entity_id=<id>`. Entity IDs come from `entities --namespace <ns> --list`. | The finding gives counts only; names appear only in `--list` output. Same name is not proof of the same person (e.g. `admin` on two mounts): confirm before merging. Merging moves aliases and can fail on conflicting aliases from one mount. |
| VT-CLI-001 | low | Most clients in a namespace are token-only (`non_entity_clients` > 50%, at least 50 clients). Each token without an entity counts as its own client. | Move workloads from direct token creation (orphan tokens, token roles) to an auth method that maps to entities (AppRole, Kubernetes, JWT). Where token roles must stay, set `allowed_entity_aliases` on the role and create tokens with `entity_alias=<name>`. | `evidence.source == "current_month"` means the billing period was empty and the month in progress was judged instead. |
| VT-CLI-002 | low | The latest month's clients exceed the average of up to 3 previous months by more than 50% (at least 100 clients). `evidence.month` may be the month in progress. | No catalogue command: compare `top_namespaces` between `usage` runs to find where the growth is. Look for CI jobs logging in per step, apps without token caching (Vault Agent), or a new per-run identity (see VT-CLI-003). | Real onboarding also causes growth; confirm with the namespace owners. A partial current month understates the real growth. |
| VT-CLI-003 | low | At least 90% of a mount's clients in the latest full month were new, and the mount already had clients the month before (at least 50 clients). Identities are created per login or run instead of reused. | No catalogue command: read the mount's roles (operator, e.g. `vault read -namespace=<ns> auth/<path>role/<name>`) and make the identity stable: JWT/OIDC `user_claim` per workload (not per run), one AppRole per application (not per instance), Kubernetes `alias_name_source` set to the service account. | Uses billing-period months only: the first month of any window reports every client as new, so it is never judged. |
| VT-CLI-004 | info | On Enterprise, more than 80% of clients are in the root namespace (at least 50 clients). | No catalogue command: plan tenant namespaces and move teams' auth and secrets into them over time. | Fine for single-team clusters; only a finding when tenants share root. |

### ACL policy permissions

These come from `policies` (needs the read-only `vault-ops-policy-reader` add-on). The script parses each policy in memory and reports only the policy name, flagged paths and capabilities, never the body. Each `path` rule is judged on its own: a `deny` elsewhere in the policy, or another policy on the same token, can narrow it, and the skill cannot see which tokens or entities hold a policy. Review the full body before changing anything. Policies are usually copied into many namespaces, so fix the source (policy-as-code) and re-apply, rather than editing copies one by one.

| rule_id | Sev | What it means | Draft remediation | Watch out for |
| --- | --- | --- | --- | --- |
| VT-POL-001 | medium | A rule on a path that matches everything in the namespace (`*`, `+/*`, …) grants `create`/`update`/`patch`/`delete` or `sudo` (`evidence.paths`): effectively admin there, including child namespaces under the glob. | Review: `vault policy read -namespace=<ns> <name>`. Replace the wildcard with the specific mounts and paths the holders need, then re-apply from source: `vault policy write -namespace=<ns> <name> <file>`. Keep a separate break-glass admin policy with tight token TTLs if one is needed. | Find who holds it first (groups, entities, auth roles); narrowing it can lock out operators. Read-only wildcards (`read`/`list` on `*`) are not flagged but still expose every secret. |
| VT-POL-002 | medium | Write access to an area that controls access (`evidence.areas`, `evidence.paths`): ACL policies, auth methods, secrets engines, namespaces, token creation or token roles, identity entities, aliases or groups. A holder can grant itself or others more access. | Review: `vault policy read -namespace=<ns> <name>`. Limit the rule to the exact paths needed (e.g. one token role instead of `auth/token/create`, specific policy names instead of `sys/policies/acl/*`) and use `allowed_parameters` to restrict values such as `policies`. Re-apply from source with `vault policy write`. | Some of these are the policy's purpose (a policy-admin or IAM role); then confirm the holders are few and audited rather than removing it. `auth/token/create` without parameter limits can mint tokens with any policy the caller holds. |
| VT-POL-003 | low | The policy grants `sudo` (`evidence.sudo_paths`), which unlocks root-protected endpoints on those paths. | Review: `vault policy read -namespace=<ns> <name>`. Remove `sudo` unless the path is root-protected and the holder needs it; re-apply with `vault policy write`. | `sudo` on exact read-only list paths (e.g. `vault-ops-readonly` on `sys/audit` and `sys/storage/raft/snapshot-auto/config`) is expected and low risk. `sudo` on a wildcard is also VT-POL-001. |
| VT-POL-004 | low | A policy name exists in several namespaces with different bodies (`evidence.variants`, `evidence.outliers`, `evidence.examples`): copies have drifted. | Compare an outlier with a typical copy: `vault policy read -namespace=<ns> <name>` in each. Decide which is right, update the source and re-apply to every namespace with `vault policy write`. | Differences can be deliberate (per-environment paths). The finding gives namespaces only; bodies are not compared in the output. |
| VT-POL-005 | info | A policy body could not be parsed, so it was not assessed. | Review by hand: `vault policy read -namespace=<ns> <name>`. | Usually unusual HCL (heredocs, odd quoting). Vault accepted it, so it is valid; the skill's parser is the limit. |

### Sentinel policies

Every VT-SNT rule needs Sentinel policy bodies, which the token reads only with the read-only `vault-ops-sentinel-reader` add-on; without it, coverage denies `sentinel EGP/RGP policy bodies` and no VT-SNT rule is judged. VT-SNT-001..004 come from `audit` and `policies` with identical fingerprints; VT-SNT-005..007 from `policies` only. The script hashes and scans each body in memory and reports names, enforcement levels, EGP paths and import names, never the source.

| rule_id | Sev | What it means | Draft remediation | Watch out for |
| --- | --- | --- | --- | --- |
| VT-SNT-005 | low | An EGP or RGP name exists in several namespaces with different bodies (`evidence.variants`, `evidence.outliers`, `evidence.examples`): copies have drifted. | Compare an outlier with a typical copy: `vault read -namespace=<ns> sys/policies/<egp\|rgp>/<name>` in each. Decide which is right, update the source and re-apply it to every namespace with `vault write -namespace=<ns> sys/policies/<egp\|rgp>/<name> enforcement_level=<level> policy=@<file> [paths=...]`. | Differences can be deliberate (a stricter copy in a regulated namespace). Re-applying a body with a stricter rule can start blocking requests. |
| VT-SNT-006 | medium | A `hard-mandatory` policy whose `main` is always false (`evidence.paths` for an EGP): it denies every request it applies to, and nothing can override it. | Review: `vault read -namespace=<ns> sys/policies/<egp\|rgp>/<name>`. If callers are locked out, an operator whose own requests the policy doesn't cover (or a root token) relaxes it first: `vault write -namespace=<ns> sys/policies/<egp\|rgp>/<name> enforcement_level=advisory policy=@<file> [paths=...]`, then fixes or deletes it (`vault delete -namespace=<ns> sys/policies/<kind>/<name>`). | An EGP applies to root tokens too, so on wildcard paths it can block the fix itself; check `paths` before any change. The rule only spots a literal `false` main, not one that is false in practice. |
| VT-SNT-007 | info | The policy imports `http` (`evidence.imports`): each request it applies to can wait on an outbound call, so that endpoint's availability and latency gate Vault requests. | Review: `vault read -namespace=<ns> sys/policies/<egp\|rgp>/<name>`. Prefer data Vault already has (request, identity, time); if the call is needed, narrow EGP `paths` and confirm the endpoint's timeout and failure behaviour. | The import alone is flagged, even when `main` never calls it; a failing call can deny requests under `hard-mandatory`. |

## Severity ranking guidance

Rank for the environment, not just by severity label:

1. `coverage.complete == false` comes first — every conclusion is partial.
2. VT-HLTH-001/002, VT-LIC-001, VT-AUD-001 and VT-SNAP-001/002 (cluster-wide availability, lifecycle, audit trail and recoverability); VT-POL-001/002 (policies that grant admin or let holders raise their own access); VT-SNT-006 (hard-mandatory deny-all, a lockout risk).
3. VT-HLTH-006 (lease growth threatens availability), VT-POL-003 (sudo), VT-MOUNT-001 (breaks on upgrade), VT-SNT-004/001 (controls that don't control), VT-SNT-005 (drifted Sentinel copies), VT-AUD-003 (secrets or accessors in audit logs), VT-AUD-002 (one audit sink can block all requests).
4. VT-AUTH-001, VT-MOUNT-002, VT-MOUNT-004 grouped by mount type; VT-LEASE-001; VT-HLTH-005 (credentials possibly still live at a backend); VT-POL-004 (drifted policy copies); client and identity anti-patterns (VT-ID-004/005, VT-CLI-001..003), which grow cost and identity sprawl.
5. Info rules — summarise counts, list examples, don't enumerate hundreds.

Group repetitive findings (same rule, same mount type across many namespaces) into one item with a count and three examples.
